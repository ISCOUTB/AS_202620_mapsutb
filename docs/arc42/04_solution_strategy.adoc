[[section-solution-strategy]]
== Estrategia de solución

=== Resumen de decisiones clave

* *Patrón arquitectural:* monolito — una sola app Flutter, sin backend propio por ahora.
* *Tecnología:* Flutter (un solo código base). Hoy se publica solo como web en Firebase Hosting (ADR 0007); la compilación móvil (Android/iOS) no está configurada.
* *Mapa del campus:* plano propio (grafo peatonal y geometría del campus) alojado localmente, superpuesto sobre el mapa base de **teselas de OpenStreetMap** dibujadas con `flutter_map` (ADR 0012, que reemplazó a Google Maps SDK).
* *Ruteo:* cálculo de la ruta más corta dentro del campus mediante **Dijkstra** sobre el grafo peatonal propio; no depende de un servicio externo de ruteo.
* *Dependencias externas:* las teselas de **OpenStreetMap** (mapa base, sin key) y, de forma opcional, dos APIs de Google — **Geocoding API** (conversión de coordenadas y direcciones) y **Static Maps API** (miniaturas) —, apagadas en producción por falta de key (ADR 0009); la analítica va por Measurement Protocol según los secretos del despliegue. Todas vía HTTPS. El GPS del dispositivo (vía el paquete `geolocator`, ADR 0017) es la única fuente de datos que no pasa por una API de red.
* *Patrones de diseño internos:* Repository, Adapter, Observer (detalle en link:../adr/0001-patrones-de-diseno.md[ADR 0001]).
* *Proceso:* ADRs para decisiones estructurales; uso de IA generativa documentado en link:../ia.md[ia.md]; equipo de 4 estudiantes, un semestre académico.

=== Decisiones tecnológicas

[options="header",cols="2,2,3"]
|===
|Decisión|Elección|Motivación
|Framework de la app|Flutter|Un solo código base multiplataforma, dado el tamaño del equipo (ver 02_architecture_constraints)
|Backend|Ninguno por ahora|El alcance actual no lo requiere; toda la lógica corre en el cliente
|Mapa base|`flutter_map` + teselas de OpenStreetMap (ADR 0012)|Evita construir un motor de renderizado de mapas propio y no exige key ni tarjeta (Google Maps SDK, la elección inicial, sí las exige); el plano del campus se superpone sobre él como capa adicional
|Origen del plano del campus|Activos locales del proyecto (grafo peatonal + geometría)|El ruteo interno y la superposición visual no dependen de que Google exponga esos datos
|Geocodificación|Google Geocoding API (opcional; apagada en producción, ADR 0009)|Evita implementar conversión de coordenadas↔direcciones propia
|Obtención de ubicación del usuario|`geolocator` (paquete de Flutter) + `FiltroUbicacion` (ADR 0017)|GPS estándar del dispositivo; expone un `Stream` de posición en tiempo real, sin requerir cámara ni una API de red adicional. El filtro descarta lecturas viejas, imprecisas o sin movimiento; sin GPS, el usuario marca la partida a mano
|===

=== Decisión de descomposición de alto nivel

El patrón arquitectural (monolito) ya está resuelto y no se compara aquí
contra alternativas. Lo que se decide en este corte es cómo se organiza
el código *dentro* de ese monolito, mediante tres patrones de diseño —
no arquitecturales —, cada uno resolviendo un problema puntual del
proyecto:

[options="header",cols="3,1"]
|===
|Problema de diseño|Patrón elegido
|Servir el plano del campus y los datos de zonas/puntos de interés (el contenido panorámico está diferido con el tour)|Repository
|Aislar al resto de la app del mapa base (`flutter_map` + OSM), Google Geocoding API, Static Maps API y Measurement Protocol|Adapter
|Ubicación en tiempo real hacia las pantallas de mapa y ubicación|Observer (`Stream` de Dart, vía `geolocator`)
|===

El ruteo interno (Dijkstra sobre el grafo peatonal propio) no se resuelve
con un patrón de diseño adicional: es un servicio propio (`ServicioRuteo`)
que no lee ningún repositorio. `MapaScreen` obtiene el grafo de
`MapaRepository` y las zonas de `ZonaRepository`, y le pasa el grafo a
`ServicioRuteo` para calcular la ruta, según se detalla en la vista de
bloques (sección 5).

El detalle de cada decisión, las alternativas descartadas y sus
consecuencias están en link:../adr/0001-patrones-de-diseno.md[ADR 0001]
(sección 9 de arc42, _Decisiones de arquitectura_). La ubicación de
estos patrones en el código fuente (`repositories/`, `adapters/`,
`services/`, `features/`) se detalla como vista de bloques de
construcción en la sección 5.

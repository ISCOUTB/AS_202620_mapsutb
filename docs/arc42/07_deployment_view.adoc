== Vista de Despliegue

MAPSUTB es un monolito Flutter sin backend propio (ADR 0004). Se despliega en dos entornos que
comparten el mismo código y los mismos artefactos de build:

* *Público* — la app compilada a web, alojada en Firebase Hosting, plan Spark (ADR 0007). Es el entorno que se
  evalúa y sobre el que se hace la sustentación.
* *Reproducible* — el mismo sitio en un contenedor nginx (`infra/`), para el servidor del
  laboratorio o cualquier máquina con Docker.

La app móvil (Android/iOS) se instala desde el build local (`flutter run`); no se distribuye por
tiendas.

Motivación::
Sin backend propio, lo único que hay que alojar son estáticos. Firebase Hosting (plan Spark) los
sirve gratis, sin método de pago y con HTTPS desde fuera de la universidad (restricciones de §2);
permite revertir a una versión publicada anterior en un paso y concentra en un proyecto de Firebase
las piezas que recomendó el docente.

Características de Calidad/Rendimiento::
* Disponibilidad y latencia del despliegue medidas por la sonda (Escenario 6: ≥ 99 % y p95 del
  health < 1 s en 7 días).
* Ante fallos de red o de las APIs externas, la app muestra errores controlados (Escenario 3).
* Logs estructurados en JSON: en la app (`lib/core/log.dart`, consola del navegador o logcat) y en
  nginx para el entorno Docker (§8).

Mapeo de los Bloques de Construcción a Infraestructura:::
Todos los bloques de §5 (pantallas de `features/`, `ZonaRepository`, `UbicacionService`,
adaptadores de `adapters/`) se empaquetan en un único artefacto (`build/web` o el APK/IPA) y se
ejecutan en el cliente. Los datos del catálogo (`assets/data/zonas.json`) viajan dentro del mismo
artefacto.

=== Nivel de Infraestructura 2

==== Pipeline de despliegue (`deploy.yml`)

. `flutter pub get --enforce-lockfile` y `flutter test`.
. `flutter build web --base-href /AS_202620_mapsutb/` con las credenciales tomadas de los secrets
  (vacías si no existen).
. Genera `build/web/health.json` con el SHA del commit y la hora del despliegue.
. Publica con `FirebaseExtended/action-hosting-deploy` (canal `live`) usando la cuenta de servicio
  del secret `FIREBASE_SERVICE_ACCOUNT`, y verifica que `health.json` responde 200 con el commit
  recién desplegado; si no, el run falla.

Recrear el entorno desde cero: crear el proyecto de Firebase, cargar `FIREBASE_SERVICE_ACCOUNT` y
`FIREBASE_PROJECT_ID` en el repositorio y re-ejecutar `deploy.yml` sobre `master` (pasos en el
README). Revertir: *Firebase console → Hosting → historial de versiones → Revertir*.

==== Contenedor nginx (`infra/`)

Imagen en dos etapas: `ghcr.io/cirruslabs/flutter` compila la app a web y `nginx:alpine` la sirve.
Expone el puerto 80 (8080 en el host), responde `/health` y escribe una línea JSON por petición en
stdout (`docker compose logs`).

[source,bash]
----
cp .env.example .env   # opcional: credenciales
docker compose --env-file .env -f infra/docker-compose.yml up --build
curl http://localhost:8080/health
----

== Conceptos Transversales (Cross-cutting)

=== Conceptos de dominio: mapa de contextos

MAPSUTB no tiene varios equipos ni varios sistemas heredados — es un cliente único
Flutter. Aun así, el código distingue cuatro contextos delimitados, con vocabulario y ciclo
de vida propios; tres están implementados y el Tour 360° está diferido (no implementado):

[mermaid]
....
flowchart LR
    UI["Pantallas de features<br/>(zonas, mapas_ruteo)"]

    subgraph CAT["Catálogo de lugares"]
        direction TB
        CATM["Zona → Piso → Espacio → Salón"]
    end

    subgraph POS["Posicionamiento"]
        direction TB
        POSM["Ubicación (Observer, Stream, GPS real)"]
    end

    subgraph RUT["Ruteo"]
        direction TB
        RUTM["Grafo peatonal + Dijkstra"]
    end

    subgraph TUR["Tour 360° — diferido (no implementado)"]
        direction TB
        TURM["Contenido panorámico"]
    end

    UI -->|consulta| CAT
    UI -->|se suscribe al stream| POS
    UI -->|solicita una ruta| RUT
    UI -.->|solicitaría panorámicas| TUR
    RUT -->|lee destino por id<br/>customer/supplier, solo lectura| CAT
    TUR -.->|referenciaría por id<br/>customer/supplier, solo lectura| CAT
....

* **Catálogo de lugares** — qué existe en el campus y cómo se organiza
  (`lib/models/zona.dart`, `piso.dart`, `espacio.dart`, `salon.dart`; expuesto por
  `ZonaRepository`, `lib/repositories/zona_repository.dart`). Es el contexto más maduro:
  ya implementado y con datos reales en `assets/data/zonas.json`. El nombre y los límites
  de "Zona", "Espacio" y "punto de interés" dentro de este contexto están fijados por el
  link:../adr/0006-reajuste-limites-contexto.md[ADR 0006]. +
  Aspecto relacionado: ninguno propio todavía — es un candidato no priorizado (ver
  link:../aspectos.md[docs/aspectos.md], sección de notas).
* **Posicionamiento** — dónde está el usuario ahora mismo (`lib/models/ubicacion.dart`,
  `UbicacionService`, `lib/services/ubicacion_service.dart`). GPS real con `geolocator` en
  `UbicacionServiceGps` (`lib/services/ubicacion_service_gps.dart`), filtrado por
  `FiltroUbicacion`; sin GPS, el usuario marca la partida a mano
  (link:../adr/0017-gps-real-geolocator-filtro.md[ADR 0017]). El simulador queda para
  demostraciones. +
  Aspecto relacionado: link:../aspectos.md[A-01] (localización y guiado en tiempo real).
* **Ruteo** — cómo llegar de un punto a otro: `MapaRepository` + `ServicioRuteo` (Dijkstra)
  en `lib/routing/`, sobre `assets/data/grafo.json` (link:../adr/0013-ruteo-dijkstra-grafo-propio.md[ADR 0013]). +
  Aspecto relacionado: link:../aspectos.md[A-01] (localización y guiado en tiempo real).
* **Tour 360°** — contenido panorámico de un punto. **Diferido (no implementado):** no
  existen `TourRepository`, `lib/features/tour/` ni panorámicas; declarado así también en
  `docs/c4/C2.md`. +
  Aspecto relacionado: link:../aspectos.md[A-04], declarado diferido de punta a punta.

**Relación entre contextos:** Ruteo depende de Catálogo de lugares — y Tour dependería, si
se retoma — como *customer/supplier* de solo lectura (necesitan el id de una
`Zona`/`Espacio`/`Salon` para saber a qué punto corresponde una ruta o una foto), nunca como
escritores de sus datos. No existe hoy ninguna capa anticorrupción porque no hay ningún
modelo externo (teselas de OpenStreetMap, Geocoding, Static Maps) integrado directamente en
el dominio — `MapaWidget`, `GeocodingAdapter` y `StaticMapAdapter` (patrón Adapter, ADR 0001)
ya cumplen ese papel para las integraciones que sí están construidas (A-01, A-02).

=== Conceptos de dominio: módulo → datos (dueño único)

[cols="1,2,2", options="header"]
|===
|Módulo |Dueño único de |Quién más lo toca

|`ZonaRepository` (`lib/repositories/zona_repository.dart`)
|`Zona`, `Piso`, `Espacio`, `Salon` — cargados desde `assets/data/zonas.json`
|`ZonasScreen`, `ZonaDetalleScreen` y `MapaScreen` (solo lectura); Ruteo solo conoce las
zonas por id (`GrafoPeatonal.entradas`)

|`UbicacionService` (`lib/services/ubicacion_service.dart`)
|`Ubicacion` (posición en tiempo real, en memoria vía `Stream`, nunca persistida)
|`UbicacionScreen` y `MapaScreen`, que se suscriben al mismo stream y le pasan la
posición a `ServicioRuteo` y a `MapaWidget`

|`MapaRepository` (`lib/routing/mapa_repository.dart`)
|Grafo peatonal (nodos/aristas, `assets/data/grafo.json`)
|`MapaScreen`, que le pasa el grafo a `ServicioRuteo` (Dijkstra) para calcular la ruta

|`TourRepository` — diferido (no implementado)
|Contenido panorámico 360° (imagen + id de referencia a un `Espacio`/`Salon`)
|Pantalla de tour
|===

Hoy no hay ninguna violación de este tipo en el código: cada modelo tiene exactamente un
repositorio/servicio que lo carga, y ninguno escribe sobre el archivo de otro. El riesgo
real está en lo que todavía no se ha construido (el tour, diferido) — la no conformidad #3 de
link:../../dominio_y_modularidad.md[dominio_y_modularidad.md] (que `TourRepository` no
extienda `Espacio`/`Salon` y evite dos escritores sobre el mismo árbol de modelos).

=== Observabilidad: logs estructurados y métrica

* *Logs de la app:* `lib/core/log.dart` emite una línea JSON por evento con `ts`, `nivel` y
  `evento` fijos más campos propios. Eventos instrumentados: `zonas_cargadas` / `zonas_error`
  (`ZonaRepositoryLocal`), `geocoding_ok` / `geocoding_error`, `static_map_ok` /
  `static_map_error` y `analitica_fallo_red` / `analitica_fuera_de_contrato` (adaptadores), todos
  con `duracion_ms` cuando aplica. Ejemplo:
+
[source,json]
----
{"ts":"2026-09-25T22:08:03.615Z","nivel":"info","evento":"zonas_cargadas","cantidad":11,"duracion_ms":38}
----
* *Logs del entorno Docker:* nginx escribe una línea JSON por petición (`infra/nginx.conf`,
  formato `json_mapsutb`).
* *Métrica:* disponibilidad y p95 del health check del entorno público, ligada al Escenario 6
  (link:../adr/0008-metrica-disponibilidad-sonda-actions.md[ADR 0008]).
